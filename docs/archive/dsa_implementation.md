# Архитектура и реализация открытого DSA драйвера для Xiaomi Router BE3600 (RD15 / RD16)

**Маршрутизаторы:** Xiaomi Router BE3600 (RD15 / RD16)  
**Процессор:** Qualcomm IPQ5332 (4x Cortex-A7 @ 1.1 GHz)  
**Ядро:** Linux 5.4.213 (Qualcomm CodeLinaro QSDK 12.5)  
**Коммутатор:** Motorcomm YT9215S (5-портовый GE L2 Smart Switch)  
**Подсистемы оффлоада:** Qualcomm PPE (Packet Processing Engine) + SFE / ECM  

---

## 1. Архитектурный обзор и предпосылки

### 1.1. Проблемы устаревшей схемы со swconfig
В заводской прошивке Xiaomi и в ранних версиях кастомных сборок проводная сеть функционировала через устаревший интерфейс `swconfig`:
* **Фантомный `switch0`**: Рудимент референсных плат Qualcomm QSDK (AP-MI04), отсутствовавший на плате BE3600.
* **Изоляция портов через VLAN (`switch1`)**: Внешний коммутатор YT9215S изолировал порты через теги `eth0.1..eth0.4`.
* **Ограничения**:
  * Необходимость фонового демона/воркера опроса линков (`netif_carrier_on/off` на суб-интерфейсах).
  * Сложность интеграции со стандартным стеком Linux (`bridge vlan`, `ip link`) и `netifd` OpenWrt.
  * Ограничения при создании пользовательских сетей и интеграции со стандартными средствами маршрутизации.

### 1.2. Решение: Нативная архитектура Linux DSA
Для полной интеграции в современный сетевой стек OpenWrt реализован нативный драйвер распределенной архитектуры коммутаторов Linux **DSA (Distributed Switch Architecture)**:
1. Каждый физический порт коммутатора представлен в системе полноценным сетевым интерфейсом (`port1` WAN, `port2` LAN 1, `port3` LAN 2, `port4` LAN 3/2.5G).
2. Управление портами осуществляется стандартными утилитами Linux (`ip link`, `bridge`) и подсистемой `netifd`.
3. Состояние линков портов отслеживается аппаратно по прерываниям PHY без задержек и циклических воркеров.
4. Аппаратный кремниевый оффлоад Qualcomm PPE и SFE полностью сохранен за счет механизма маскировки DSA-портов под IEEE 802.1Q VLAN.

## 2. Что разработано с нуля

### 2.1. Пакет открытого драйвера коммутатора (`package/kernel/yt-921x-dsa`)
Создан полностью открытый модуль ядра `kmod-yt-921x-dsa`, состоящий из драйвера коммутатора и собственного теггера:

1. **Теггер протокола IEEE 802.1Q (`src/tag_yt921x.c`)**:
   * Зарегистрирован протокол тегирования `DSA_TAG_PROTO_YT921X`.
   * Передача (`yt921x_tag_xmit`): вставляет стандартный 4-байтовый заголовок IEEE 802.1Q CTAG (`0x8100`) с VID, соответствующим индексу порта (`yt921x_port_to_vid`). Использование стандартного 802.1Q заголовка гарантирует нативный аппаратный расчет L4-контрольных сумм контроллером EDMA v2 процессора IPQ5332.
   * Прием (`yt921x_tag_rcv`): извлекает VID из заголовка, определяет входной slave-порт (`yt921x_vid_to_port`), выполняет $O(1)$ удаление тега со сдвигом заголовка Ethernet (`skb_pull_rcsum` + `memmove`) и передает чистый нетегированный фрейм в сетевой стек.
2. **Драйвер коммутатора (`src/yt921x.c` и `src/yt921x.h`)**:
   * Реализует структуру `struct dsa_switch_ops` (`setup`, `port_enable`, `port_disable`, `phy_read`, `phy_write`, `get_stats64`).
   * Аппаратная конфигурация YT9215S:
     * Для CPU-порта (Port 5) включен режим `YT921X_EGR_TAG_MODE_TAGGED`.
     * Для внешних медных портов включен режим `YT921X_EGR_TAG_MODE_UNTAGGED`.
     * Отключен механизм `YT921X_EXT_CPU_PORT`, вызывавший отправку пакетов на CPU в обход egress-тегирования.
     * Флудинг неизвестных кадров ограничен рамками изолированного VLAN конкретного порта и CPU.
   * Аппаратная статистика портов (`get_stats64`): считывает значения счетчиков непосредственно из 64-битных кремниевых регистров MIB коммутатора для корректного отображения в LuCI.
   * Управление прерываниями и линками PHY: мгновенная передача событий подключения/отключения кабеля в стек Linux без polling-потоков.

### 2.2. Платформенные механизмы унификации сетевых портов
* **Скрипты `85_rename_eth1` и `01-rename-port4` (RD15)**:
  * В сабтаргете RD15 четвертый проводной порт (2.5G PHY QCA8081 / YT8821) подключен к независимому GMAC-контроллеру `eth1`, в то время как на RD16 все 4 порта обслуживаются свитчем YT9215S (порт 0 свитча).
  * На этапе preinit (`target/linux/ipq53xx/rd15/base-files/lib/preinit/85_rename_eth1`) и hotplug (`etc/hotplug.d/net/01-rename-port4`) интерфейс `eth1` безопасно переименовывается в `port4`, обеспечивая полностью унифицированную схему сетевых интерфейсов (`port1`..`port4`) для обеих модификаций роутера.

## 3. Что бэкпортировано

### 3.1. Бэкпорты в подсистему DSA ядра Linux 5.4 (`patches-5.4/909-net-dsa-backport-helpers.patch`)
Для функционирования современного DSA и интеграции с вендорными акселераторами в ядро 5.4 сабтаргетов `rd15` и `rd16` бэкпортированы:
1. **Экспортируемые функции DSA**:
   * `dsa_slave_dev_check()` — проверка, является ли сетевое устройство slave-портом DSA.
   * `dsa_port_from_netdev()` — получение указателя `struct dsa_port` из `net_device`.
2. **Аппаратный хук MIB статистики `get_stats64` (из upstream Linux 5.12+)**:
   * В `struct dsa_switch_ops` добавлен коллбэк `void (*get_stats64)(struct dsa_switch *ds, int port, struct rtnl_link_stats64 *stats);`.
   * В `net/dsa/slave.c` (`dsa_slave_get_stats64`) добавлена прямая диспетчеризация вызова в драйвер свитча при наличии хука.
3. **Автоматическое открытие мастер-интерфейса (из upstream Linux 5.12+)**:
   * В `dsa_slave_open()` вызов проверки флага заменен на `dev_open(master, NULL)`. При поднятии любого slave-порта DSA мастер-интерфейс `eth0` переводится в состояние UP автоматически. Это устранило необходимость в фиктивной секции `interface 'eth0'` в UCI `/etc/config/network` и скрыло `eth0` из списка интерфейсов LuCI.
4. **Поддержка альтернативного имени узла портов в Device Tree**:
   * В `net/dsa/dsa2.c` добавлена проверка имени узла `ethernet-ports` наряду с `ports`.
5. **Протоколы и нотификаторы**:
   * Добавлен протокол `DSA_TAG_PROTO_YT921X` (`21`), событие `DSA_NOTIFIER_TAG_CHG` и инлайн-хелперы блокирующих нотификаторов.

### 3.2. Обновление кодовой базы ядра до QSDK 12.5 (`commit c2ca06284375`)
* **Многоядерный ресайклинг SKB (`skbuff_recycle.c`)**: механизм `skb_recycler_consume_list_fast` для мультипроцессорных платформ (`CONFIG_SKB_RECYCLER_MULTI_CPU`), оптимизирующий сетевой стек 4-ядерного IPQ5332.
* **MDIO API**: экспортируемые функции прямого доступа к шине MDIO `qca_mii_read`/`qca_mii_write`.

## 4. Где и какие патчи были сделаны

### 4.1. Патчи ядра Linux 5.4 (`target/linux/ipq53xx/{rd15,rd16}/patches-5.4/`)
* **`908-netdevice-dsa-abi-compat.patch`**:
  * Переносит указатель `struct dsa_port *dsa_ptr;` в самый конец структуры `struct net_device`.
  * Сохраняет смещения всех стандартных полей байт-в-байт (`netdev_ops` = 296, `flags` = 316, `type` = 348), предотвращая Kernel Panic в закрытых бинарных блобах Wi-Fi вендора (`umac.ko`, `wifi_3_0.ko`).
* **`909-net-dsa-backport-helpers.patch`**:
  * Включает константу `DSA_YT921X_VID_BASE = 4000` в `<net/dsa.h>`.
  * Добавляет инлайн-хелперы $O(1)$: `dsa_slave_to_master(dev)` и `dsa_slave_to_vid(dev)` (маппинг портов 1..3 в VID 4001..4003, порт 0 в VID 4004).

### 4.2. Патчи аппаратного ускорения Qualcomm (PPE / ECM / SFE)
* **`package/kernel/qca-nss-ppe-vlan/patches/0002-vlan-mgr-support-dsa-slave-ports.patch`**:
  * Модуль `nss_ppe_vlan_mgr.c` распознает DSA slave устройства через `dsa_slave_dev_check(dev)` и транслирует их в PPE как VLAN-интерфейсы на базовом GMAC `eth0` с системными VID 4001..4004.
  * Устанавливает `is_vlan_as_vp = false`, направляя трафик через быструю аппаратную трансляцию тегов PPE (`ppe_drv_vlan_add_xlate_rule`).
* **`package/kernel/qca-nss-ppe-bridge/patches/0001-bridge-mgr-support-dsa-slave-ports.patch`**:
  * Разрешает DSA slave netdevices в проверках `is_ppe()` и перенаправляет операции моста в `nss_ppe_vlan_mgr_join_bridge` / `leave_bridge`, активируя аппаратную коммутацию моста `br-lan` в PPE.
* **`package/kernel/qca-nss-ecm/patches/0002-ecm-support-dsa-slave-ports-as-vlan.patch`**:
  * Регистрирует интерфейсы DSA в базе соединений ECM с типом `ECM_DB_IFACE_TYPE_VLAN`, тегом `dsa_slave_to_vid(dev)` и родителем `eth0`.
  * Обеспечивает сквозной спуск по иерархии интерфейсов до физического GMAC.
* **`package/kernel/qca-nss-ecm/patches/0003-ecm-sfe-frontend-support-dsa-slave-ports.patch`**:
  * Изолирует DSA slave порты во фронтенде программного ускорителя SFE.
  * Привязывает правила ускорения SFE непосредственно к DSA slave netdev (`portX`) без программного тега VLAN, устраняя несоответствие интерфейсов и сброс сессий при передаче между LAN и Wi-Fi.

### 4.3. Конфигурация платформы сабтаргетов RD15 и RD16
* **Device Tree (`ipq5332-rd15.dts`, `ipq5332-rd16.dts`)**:
  * Добавлен узел `switch0: switch@1d` под шиной MDIO (`/soc/mdio@90000`) с аппаратным сбросом на GPIO 51.
  * Описаны внутренние PHY (`sw_phy0`..`sw_phy4`) и пользовательские порты (`port1`..`port3` на RD15, `port1`..`port4` на RD16).
  * CPU-порт (Port 8 коммутатора) привязан к интерфейсу `dp1` (`eth0`) в режиме `2500base-x` (fixed-link 2.5 Gbps).
* **Сетевой стек OpenWrt**:
  * `target.mk`: пакет `kmod-yt-9215s-driver swconfig yt-9215s-client` заменен на `kmod-yt-921x-dsa`.
  * `etc/config/network`: чистая схема моста `br-lan` с портами `port2..port4`, WAN на `port1`. Отключен GRO (`option gro '0'`) на 2.5G порту `port4` для предотвращения фрагментации при оффлоаде.
  * `etc/board.d/01_network`: вызов `ucidef_set_interfaces_lan_wan "port2 port3 port4" "port1"`.

## 5. Исправления в существующем (старом) коде

В ходе интеграции были выявлены и устранены скрытые дефекты в базовом и стороннем коде:

1. **Ошибки кремниевых MIB-счетчиков в открытом драйвере YT921x**:
   * *Инверсия 64-битных слов*: в функции `yt921x_read_mib` младшее слово считывалось в `val0`, а старшее в `val1`, но сборка выполнялась как `((u64)val0 << 32) | val1`. Это приводило к скачку счетчика на 4 ГБ ($2^{32}$) при передаче каждого байта. Исправлено на: `val = ((u64)val1 << 32) | val0;`.
   * *Смещения регистров в таблице дескрипторов MIB*: исправлены некорректные адреса регистров:
     * `RxGoodBytes`: `0x38` $\to$ **`0x3C`** (64-битный `RxOkByte`).
     * `RxBadBytes`: `0x40` $\to$ **`0x44`** (64-битный `RxNoOkByte`).
     * `RxOverSzErr`: `0x48` (размер 2) $\to$ **`0x4C`** (32-битный `RxOverFlow`, размер 1).
     * `TxGoodBytes`: `0x80` $\to$ **`0x84`** (64-битный `TxOkByte`).
     * `TxCollision`: `0x88` (размер 2) $\to$ **`0x8C`** (32-битный `TxCollision`, размер 1).
   * *Опечатка проверки переполнения 32-битных регистров*: в выражении `if (val < (u32)val)` переменная сравнивалась сама с собой; исправлено на `if (val0 < (u32)val)`.
2. **Защита хука быстрого пути в сетевом ядре (`net/core/dev.c`)**:
   * В функции `__netif_receive_skb_core()` вызовы проприетарного быстрого пути `athrs_fast_nat_recv(skb)` выполнялись до `rx_handler` DSA-теггера. В результате SFE перехватывал кадры на мастер-интерфейсе `eth0` до того, как драйвер DSA успевал снять тег 802.1Q и подменить интерфейс на `portX`.
   * Вызовы защищены проверкой `!netdev_uses_dsa(skb->dev)`, что гарантирует корректную передачу пакетов в DSA-теггер.
3. **Состояние гонки в Netfilter NAT ядра QSDK 12.5 (`net/netfilter/nf_nat_core.c`)**:
   * Устранено состояние гонки при повторном добавлении `ct` в список `nat_bysource`.
4. **Стабильность инициализации PCIe для чипа Wi-Fi 5 GHz QCN6432**:
   * В `drivers/pci/controller/dwc/pcie-qcom.c` добавлен механизм повторной инициализации линка (`enable-enum-retry`), устраняющий сбой детекции чипа при холодном старте.

## 6. Как это сейчас работает (End-to-End Packet Flow)

### 6.1. Движение входящего пакета (Ingress: из внешней сети в роутер)
1. Кадр поступает на внешний медный порт свитча (например, `Port 2` / LAN 1).
2. Свитч Motorcomm YT9215S накладывает аппаратный тег IEEE 802.1Q CTAG с VID `4002` (`DSA_YT921X_VID_BASE + 2`) и передает кадр в процессор через CPU Port 5 (`dp1` / `eth0`).
3. Сетевой контроллер EDMA v2 процессора IPQ5332 на интерфейсе `eth0` нативно проверяет L4-контрольные суммы 802.1Q фрейма.
4. **Аппаратный путь (PPE)**:
   * Акселератор PPE по тегу `VID 4002` на `eth0` определяет виртуальный входной порт (`port2`).
   * Если сессия присутствует в Flow Table PPE: выполняется аппаратная маршрутизация/коммутация (подмена IP/MAC/VLAN) прямо в кремнии и немедленная отправка в целевой интерфейс (WAN, Wi-Fi или другой LAN-порт).
5. **Программный путь (Slow-Path / SFE)**:
   * Если сессия новая или не подлежит аппаратному оффлоаду: пакет передается в сетевой стек ядра.
   * Теггер `tag_yt921x.c` перехватывает кадр, извлекает VID `4002`, определяет slave-устройство `port2`, выполняет $O(1)$ удаление тега и передает чистый пакет в интерфейс `port2`.
   * Сетевой стек Linux и SFE обрабатывают пакет штатным образом.

### 6.2. Движение исходящего пакета (Egress: из роутера в кабель)
1. Сетевой стек Linux направляет пакет в интерфейс `port2`.
2. Теггер `tag_yt921x.c` вставляет 4-байтовый 802.1Q тег с VID `4002` и передает кадр в мастер-интерфейс `eth0`.
3. Коммутатор YT9215S принимает кадр на CPU Port 5, считывает VID `4002`, направляет кадр в медный порт `Port 2`, срезает тег (режим Egress Untagged) и передает нетегированный Ethernet-кадр в провод клиенту.

### 6.3. Интеграция с LuCI и веб-интерфейсом
* Интерфейс `eth0` функционирует исключительно как аппаратный conduit и не отображается в списке логических сетей LuCI.
* В LuCI отображаются нативные порты `port1`..`port4`.
* Статистика переданных и принятых байт и пакетов для каждого порта считывается напрямую из кремниевых счетчиков коммутатора через бэкпортированный хук `get_stats64`, обеспечивая точный учет даже при 100% аппаратном оффлоаде PPE.
