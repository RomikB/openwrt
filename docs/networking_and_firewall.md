# Сетевой стек, Firewall4 (nftables) и методика тестирования PPE оффлоада

## 1. Архитектура сетевого экрана: Firewall4 на ядре 5.4 QSDK

В прошивке **Xiaomi Router BE3600 (RD15)** осуществлен полный переход со старого межсетевого экрана `firewall3` (`iptables`) на современный стандарт OpenWrt 24 — **`firewall4`** (`nftables 1.1.x` + `ucode`).

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Firewall4 / Netfilter Архитектура               │
│                                                                        │
│   UCI Конфигурация: /etc/config/firewall                               │
│                           │                                            │
│                           ▼                                            │
│   Генератор правил: fw4 (ucode) ───► /usr/sbin/nft (nftables 1.1.x)    │
│                                                    │                   │
│                                                    ▼                   │
│   Стек ядра Linux: Netfilter (table inet fw4, nft_*)                   │
│                           │                                            │
│                           ▼ (nf_conntrack хуки)                        │
│   Enhanced Connection Manager: ecm.ko (NF_INET_POST_ROUTING)           │
│                           │                                            │
│                           ▼ (Аппаратные правила)                       │
│   Qualcomm PPE Hardware Engine (Маршрутизация 2.5 Gbps, ~0% CPU)       │
└────────────────────────────────────────────────────────────────────────┘
```

### 1.1. Взаимодействие Firewall4 с аппаратным ускорителем Qualcomm PPE/ECM
1. **Низкоуровневые хуки ядра Linux**:
   Диспетчер аппаратного ускорения `ecm.ko` перехватывает сетевые потоки не через правила фаервола, а напрямую через системную подсистему `nf_conntrack` в точке `NF_INET_POST_ROUTING` (приоритет `NF_IP_PRI_NAT_SRC + 1`).
2. **Независимость от iptables/nftables**:
   Поскольку и старый `iptables`, и новый `nftables` работают поверх одной и той же подсистемы `nf_conntrack` ядра Linux, **модуль ECM одинаково прозрачно видит все сессии соединений и транслирует их в аппаратные таблицы PPE**.
3. **Критическое правило: запрет софтверного Flow Offloading**:
   * В `/etc/config/firewall` параметры программного оффлоада **обязательно должны быть отключены**:
     ```text
     set firewall.@defaults[0].flow_offloading='0'
     set firewall.@defaults[0].flow_offloading_hw='0'
     ```
   * *Причина:* Программный `flowtable` в `firewall4` забирает пакеты на сетевом входе (`ingress`), пересылая их силами центрального процессора в обход точки `POST_ROUTING`. В результате `ecm.ko` не получает пакеты и аппаратный ускоритель PPE не задействуется.

### 1.2. Особенности и ограничения ядра Linux 5.4
1. **Отсутствие PIPAPO Set Backend**: В ядре 5.4 отсутствует модуль `nft_set_pipapo.c` (появился в ядре 5.6). Поэтому в сетах адресов нельзя использовать составные интервалы (например, одновременный диапазон `подсеть /24` + `диапазон портов`). Обычные сеты (списки IP, списки MAC, диапазоны портов по отдельности) работают штатно.
2. **Хук моста для ECM**: В `firewall4` параметр `net.bridge.bridge-nf-call-iptables=0` выключен, L2-трафик коммутируется аппаратно матрицей YT9215S. Никаких дополнительных правил в `/etc/nftables.d/` для работы ECM не требуется.

### 1.3. Влияние на системные ресурсы
* **Оперативная память (RAM)**: Потребление оперативной памяти возрастает на **~2.0–2.5 МБ** за счет модулей `kmod-nft-*` (25 модулей ядра) и библиотек `libnftables.so` (690 КБ) и `libnftnl.so` (138 КБ).
* **Флеш-память (SquashFS)**: Суммарный оверхед в сжатом образе прошивки составляет **~500–800 КБ**.

## 3. Протокол проверки функциональности Firewall4

### Тест 1: Проверка статуса сервиса и загрузки правил
```bash
# 1. Валидация правил
fw4 check

# 2. Проверка активных таблиц
nft list tables
# Ожидается: table inet fw4

# 3. Проверка загрузки модулей ядра
lsmod | grep -E 'nft_|nf_tables'
# Ожидается: nf_tables, nft_chain_nat, nft_masq, nft_ct, nft_counter, nft_limit, nft_reject
```

### Тест 2: Проверка политик по умолчанию (Default Drop / Reject)
* Выполнение с тестового ПК из WAN:
  ```bash
  curl -m 2 http://192.168.11.24:81/
  ```
* **Критерий успеха**: Роутер немедленно возвращает `Connection refused` (TCP RST согласно цепочке `handle_reject` в nftables).

### Тест 3: Проверка разрешающих правил WAN (SSH, HTTP, ICMP)
* Проверка с тестового ПК из WAN:
  ```bash
  ping -c 3 192.168.11.24
  curl -I http://192.168.11.24/
  curl -k -I https://192.168.11.24/
  ssh root@192.168.11.24 "uptime"
  ```
* **Критерий успеха**: Все запросы успешны, счетчики в цепочке `input_wan` инкрементируются (`nft list chain inet fw4 input_wan`).

### Тест 4: Проверка изоляции LAN из WAN (Forward Filtering)
* Попытка пинга внутреннего адреса клиента из WAN:
  ```bash
  ping -c 2 -W 2 192.168.1.197
  ```
* **Критерий успеха**: Пакеты не проходят (100% loss / Destination Host Unreachable).

### Тест 5: Проверка трансляции сетевых адресов (NAT Masquerade / SNAT)
* Проверка исходящего трафика с клиента Wi-Fi на сервер WAN при запущенном `tcpdump -n -i eth0 host 192.168.11.24`:
* **Критерий успеха**: Адрес источника строго равен WAN IP роутера `192.168.11.24`. Внутренний IP `192.168.1.X` наружу не транслируется.

### Тест 6: Динамическое применение правил (Port Forwarding / DNAT)
```bash
uci add firewall redirect
uci set firewall.@redirect[-1].name='Test-DNAT'
uci set firewall.@redirect[-1].src='wan'
uci set firewall.@redirect[-1].src_dport='8888'
uci set firewall.@redirect[-1].dest='lan'
uci set firewall.@redirect[-1].dest_ip='192.168.1.197'
uci set firewall.@redirect[-1].dest_port='80'
uci set firewall.@redirect[-1].proto='tcp'
uci commit firewall
/etc/init.d/firewall reload
```
* **Критерий успеха**: Правило появляется в цепочке `dstnat_wan` (`nft list chain inet fw4 dstnat_wan`), внешнее обращение на порт 8888 перенаправляется на порт 80 клиента LAN.

## 4. Протокол проверки аппаратного ускорения (Qualcomm PPE / ECM)

### 4.1. Тест LAN (2.5G) ➔ WAN (Line Rate 2.5 Gbps)
* **Запуск iperf3 сервера на тестовом ПК WAN**:
  ```bash
  iperf3 -s -i 1
  ```
* **Запуск клиента на хосте LAN 4 (2.5G порт)**:
  ```bash
  iperf3 -c 192.168.11.103 -P 4 -t 30
  ```
* **Проверка счетчиков оффлоада на роутере во время теста**:
  ```bash
  # 1. Проверка активных соединений в базе ECM:
  cat /sys/kernel/debug/ecm/ecm_db/connection_count

  # 2. Проверка аппаратных счетчиков PPE:
  cat /sys/kernel/debug/ppe/stats

  # 3. Мониторинг нагрузки CPU:
  htop
  ```
* **Критерии успеха**:
  * Скорость передачи: **2.35–2.48 Gbps** (полный Line Rate интерфейса 2.5G).
  * Нагрузка на все 4 ядра CPU роутера: **~0–1%** (процессор не участвует в пересылке пакетов).
  * В счетчиках `ecm_db` сессии помечены флагом `accelerated = 1`.

### 4.2. Тест Wi-Fi 5 GHz (HE160) ➔ WAN
* **Клиент**: Ноутбук, подключенный к точке `OpenWrt_RD15_5G` (канал 44, полоса 160 МГц, PHY rate 2402 Mbps).
* **Запуск теста**:
  ```bash
  iperf3 -c 192.168.11.103 -P 4 -t 30
  ```
* **Проверка работы плагина Wi-Fi оффлоада**:
  ```bash
  # Проверка связывания ecm-wifi-plugin:
  dmesg | grep -i ecm_wifi_plugin
  ```
* **Критерии успеха**:
  * Реальная скорость через беспроводной мост: **1400–1800+ Mbps**.
  * Нагрузка на процессор роутера: **менее 5%**.
