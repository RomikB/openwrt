# Детальный анализ режима моста и Mesh на стоковой прошивке Xiaomi Router BE3600 (RD15)

Данный документ содержит глубокий технический анализ механизмов включения, конфигурации и функционирования режима беспроводного/проводного моста между двумя маршрутизаторами **Xiaomi Router BE3600 (RD15)** на базе **Qualcomm IPQ5332 + QCN6432 (QSDK 12.4)**.

Документ объединяет:
1. **Статический анализ скриптов и бинарников** распакованного rootfs стоковой прошивки (`tmp/rootfs/`).
2. **Эмпирическую верификацию по живым дампам телеметрии** с пары маршрутизаторов RD15, работающих в режиме моста на стоковой прошивке 1.0.87 (Master: `192.168.11.23`, Client: `192.168.11.22`).

---

## 1. Два независимых сценария режима моста в стоковой прошивке

Анализ кода и реальных дампов выявил, что в стоковой прошивке сосуществуют **два принципиально различных механизма беспроводного моста**:

```
                         ┌────────────────────────────────────────────────────────┐
                         │   Режимы беспроводного моста в Xiaomi RD15 (Stock)     │
                         └──────────────────────────┬─────────────────────────────┘
                                                    │
                 ┌──────────────────────────────────┴──────────────────────────────────┐
                 ▼                                                                     ▼
   ┌──────────────────────────────┐                                      ┌──────────────────────────────┐
   │ Сценарий А: Режим ретрансля- │                                      │ Сценарий Б: Фирменный Mesh   │
   │ тора (Wireless Relay/Bridge) │                                      │ (Xiaomi MiMesh v4 / WHC)     │
   ├──────────────────────────────┤                                      ├──────────────────────────────┤
   │ • NETMODE: 'wifiapmode'      │                                      │ • NETMODE: 'whc_re'          │
   │ • Клиентский VAP: wl02 (5G)  │                                      │ • Клиентский VAP: wl01 (5G)  │
   │ • Целевой SSID: Пользователь-│                                      │ • Целевой SSID: Скрытый      │
   │   ский (e.g. 'Xiaomi_C8F1')  │                                      │   'MiMesh_<NetworkID>' (wl5) │
   │ • Драйвер: extap='1',        │                                      │ • Драйвер: wds='1',          │
   │   4addr: on                  │                                      │   4addr: on                  │
   │ • Демоны: topomon ОТКЛЮЧЕН,  │                                      │ • Демоны: topomon АКТИВЕН,   │
   │   cab_meshd ОТКЛЮЧЕН         │                                      │   cab_meshd АКТИВЕН          │
   │ • Совместим с ЛЮБОЙ AP!      │                                      │ • Только между Xiaomi Mesh   │
   └──────────────────────────────┘                                      └──────────────────────────────┘
```

> [!IMPORTANT]
> **Данные с живого стенда показали, что роутеры работают по Сценарию А (`wifiapmode` + `extap='1'`)**:
> * **Master (`192.168.11.23`)**: работает в `NETMODE='lanapmode'` (Wired AP mode / мост к домашней сети `192.168.11.0/24`).
> * **Client (`192.168.11.22`)**: работает в `NETMODE='wifiapmode'` (Wireless Relay / Беспроводной ретранслятор), подключен по 5 ГГц к сети `Xiaomi_C8F1`.

## 2. Верифицированная архитектура Сценария А: Режим ретранслятора (`wifiapmode`)

### 2.1. Конфигурация интерфейса клиента Backhaul STA (`wl02`)

В режиме `wifiapmode` на чипе 5 ГГц (QCN6432 / `wifi1`) создается специальный STA-интерфейс `wl02` (в `misc.wireless.apclient_5G='wl02'`).

Фактическая конфигурация из дампа `/etc/config/wireless`:
```uci
config wifi-iface
    option device 'wifi1'
    option ifname 'wl02'
    option network 'lan'
    option mode 'sta'
    option ssid 'Xiaomi_C8F1'
    option encryption 'psk2'
    option enctype 'AES'
    option extap '1'               # <--- Ключевой флаг Extended AP
    option scanifname 'wl0'
    option athnewind '1'
    option disabled '0'
```

Команды ядра, выполняемые скриптом `/lib/wifi/qcawificfg80211.sh` при наличии `extap '1'`:
1. `cfg80211tool wl02 extap 1`
2. `iw wl02 set 4addr on`

Вывод `iw wl02 info` из живого дампа:
```text
Interface wl02
    ifindex 27
    wdev 0x500000003
    addr 56:4f:3b:ec:27:5f
    ssid Xiaomi_C8F1
    type managed
    channel 36 (5180 MHz), width: 160 MHz, center1: 5250 MHz
    txpower 28.00 dBm
    4addr: on                       # <--- 4-адресный режим подтвержден в ядре!
```

Параметры соединения в `iwconfig wl02`:
* **Стандарт**: IEEE 802.11bea (Wi-Fi 7 / EHT160).
* **Канальная скорость**: **2.8824 Гбит/с** (MCS 13, 2x2 MIMO, 160 МГц).
* **Сигнал**: `-60 dBm` (Link Quality 89/94).

### 2.2. Состав моста `br-lan` на клиенте и мастере

#### На стороне Client (`192.168.11.22`):
Мост объединяет локальную точку доступа, клиентский транзитный VAP и все проводные порты:
```text
bridge name     bridge id               STP enabled     interfaces
br-lan          7fff.504f3bec275c       no              bhap_mld0
                                                        eth0.1   (LAN 1 - Port 1)
                                                        eth0.2   (LAN 2 - Port 2)
                                                        eth0.3   (LAN 3 - Port 3)
                                                        eth1     (LAN 4 / 2.5G - Port 4)
                                                        wl0      (Fronthaul AP 5G)
                                                        wl02     (Backhaul STA 5G -> Master)
```

Таблица MAC-адресов моста (`brctl showmacs br-lan`):
* На порту **4 (`eth1` / 2.5G LAN)** зафиксирован проводной ПК с MAC `00:25:22:aa:62:0b` (состояние `active`, aging timer `4.46s`).
* На порту 7 (`wl02` / STA 5G) видны MAC-адреса вышестоящей сети (шлюз `192.168.11.1`, мастер `50:4f:3b:ed:07:98` и другие сетевые клиенты).
* Порты `eth0.1`, `eth0.2`, `eth0.3` (1G порты свитча YT9215S) находятся в состоянии `disabled` (кабели не подключены).

Свойства портов моста (`ip -d link show`):
* `wl02`: `master br-lan state forwarding port_no 0x7`, `hairpin off`, `isolated off`, `learning on`, `flood on`.
* `wl0`: `master br-lan state forwarding port_no 0x6`, `hairpin off`, `isolated off`, `learning on`, `flood on`.
* Порт `eth1`: `master br-lan state forwarding port_no 0x4`, `hairpin off`, `isolated off`, `learning on`, `flood on`.

#### На стороне Master (`192.168.11.23`):
Мост объединяет проводные порты и Wi-Fi 7 MLD интерфейс:
```text
bridge name     bridge id               STP enabled     interfaces
br-lan          7fff.504f3bed0798       no              bhap_mld0
                                                        eth0.1
                                                        eth0.2
                                                        eth0.3
                                                        eth1
                                                        hostap_mld0
```

> [!NOTE]
> **Архитектура Wi-Fi 7 MLD Bonding на Master**:
> Интерфейсы `wl0` (5G) и `wl1` (2.4G) не включены в `br-lan` по отдельности. Вместо этого в ядре создано bonding-устройство `hostap_mld0` (`bond mode UNKNOWN`), в которое `wl0` и `wl1` входят как слейвы (`master hostap_mld0`). В мост `br-lan` включен сам `hostap_mld0`.
> В таблице MAC-адресов моста Master на радиопорту 6 (`hostap_mld0`) отображается **только один MAC-адрес: `56:4f:3b:ec:27:5f` (собственный MAC STA-адаптера `wl02` клиента)**. Реальный MAC проводного ПК `00:25:22:aa:62:0b` в таблице Master полностью отсутствует.

### 2.3. Сетевой уровень и отключение сервисов в `wifiapmode`

1. **IP-адресация (`dhcp_apclient.sh`)**:
   * При старте скрипт запускает `udhcpc` на `br-lan`.
   * Получив аренду от шлюза (`192.168.11.1`), скрипт фиксирует параметры в `/etc/config/network`:
     ```uci
     set network.lan.proto='static'
     set network.lan.ipaddr='192.168.11.22'
     set network.lan.gateway='192.168.11.1'
     set network.lan.dns='192.168.11.7'
     ```
   * В таблице маршрутизации: `default via 192.168.11.1 dev br-lan proto static`. Все устройства находятся в **единой подсети `192.168.11.0/24`**.
2. **Фаервол (100% подтверждено дампом)**:
   * Вывод `iptables-save`, `ip6tables-save`, `arptables` и `ebtables` на клиенте показал:
     * Таблицы `filter`, `nat`, `mangle`, `raw` **полностью пусты**.
     * Политика всех цепочек — `ACCEPT`.
     * NAT-маскарадинг отсутствует.
3. **Демоны**:
   * `dnsmasq` запущен только как DNS-прокси/кэш, DHCP-сервер переведен в `ignore="1"`.
   * `odhcpd`, `trafficd`, `miqos` остановлены.
   * `topomon`, `cab_meshd`, `meshd` **не запущены** (`/var/run/topomon` пуст).

### 2.4. Аппаратное ускорение PPE и ECM в `wifiapmode`

Вывод системных параметров акселератора на клиенте из живого дампа:
* `/proc/sys/net/ecm/ppe_fse_enable`: **`1`** (Flow Search Engine в кремнии PPE активен).
* `/proc/sys/net/ecm/sfe_fast_xmit_enable`: **`1`** (быстрая передача SFE активна).
* `/proc/sys/net/ecm/sfe_fse_enable`: **`1`** (аппаратный оффлоад SFE FSE активен).
* `/proc/sys/net/ecm/sfe_mht_enable`: **`1`** (поддержка Multi-Hardware Table активна).
* `/proc/sys/net/ecm/src_interface_check`: **`0`** (проверка входного интерфейса отключена — критично, чтобы пакеты после трансляции MAT не сбрасывались ядром).
* `/proc/sys/ppe/bridge_mgr/fdb_disabled`: **`1`**.
* Счетчик сессий `/sys/kernel/debug/ecm/ecm_db/connection_count`: **`13`** активных ускоряемых соединений.
* Модули ядра: `ecm`, `ecm_wifi_plugin`, `emesh_sp`, `qca_nss_ppe`, `qca_nss_sfe` загружены.

> [!TIP]
> Поскольку `fdb_disabled=1`, традиционный Bridge Manager FDB learning отключен; ускорением мостового трафика между Wi-Fi Direct Connect (`wl02`) и портами свитча занимается **Qualcomm ECM с плагином `ecm_wifi_plugin.ko` через Flow Search Engine (FSE)** с отключенной проверкой входных интерфейсов (`src_interface_check=0`).

## 3. Сценарий Б: Режим фирменного Mesh (`whc_cap` $\leftrightarrow$ `whc_re`)

Этот режим задействуется при спаривании роутеров аппаратной кнопкой **Mesh** на корпусе, через меню Mesh веб-интерфейса или через мобильное приложение Mi Home. В этом режиме стек прошивки переходит в состояние **MiMesh v4 (Whole Home Coverage / WHC)**:

### 3.1. Выделенная транзитная сеть Backhaul (WDS VAP)
В отличие от режима ретранслятора, где клиент цепляется к обычной пользовательской точке доступа, в режиме Mesh создаются **выделенные скрытые служебные интерфейсы**:
* **На стороне Master (CAP / `whc_cap`)**:
  * Функция `__init_wifi_bh_ap` из `/lib/mimesh/mimesh_init.sh` поднимает скрытые точки доступа:
    * `wl4` (2.4 ГГц): SSID `MiMesh_<NetworkID>`, шифрование WPA2-PSK (уникальный ключ сети).
    * `wl5` (5 ГГц): SSID `MiMesh_<NetworkID>`, шифрование WPA2-PSK.
  * Флаги конфигурации в UCI:
    ```uci
    option backhaul '1'
    option backhaul_ap '1'
    option wds '1'
    option hidden '1'
    ```
* **На стороне Satellite (RE / `whc_re`)**:
  * Функция `__init_wifi_bh_sta` создает беспроводные клиенты backhaul:
    * `wl10` (2.4 ГГц STA) и `wl01` (5 ГГц STA).
  * Флаги конфигурации в UCI:
    ```uci
    option mode 'sta'
    option network 'lan'
    option backhaul '1'
    option wds '1'
    option disabled '0'
    ```
* **Канальный уровень (L2 в радиоэфире)**:
  * В драйвере `wifi_3_0.ko` для пира выставляется флаг **`wds_enabled = 1`**.
  * Передача кадров осуществляется в формате **True 4-Address WDS (IEEE 802.11)**: заголовок содержит 4 MAC-адреса (RA, TA, DA, SA).
  * **Отсутствует подмена MAC (без MAT)**: Master напрямую обучается реальным MAC-адресам всех клиентов, подключенных к сателлиту, и видит их в локальной таблице моста `br-lan`.

### 3.2. Демон контроля топологии и предотвращения петель `topomon`
Центральным компонентом Mesh является демон `/usr/sbin/topomon` и его скрипт управления `/usr/sbin/topomon_action.sh`:
1. **Динамический выбор среды передачи (Wired vs Wireless Failover)**:
   * Демон непрерывно опрашивает состояние физических линков Ethernet (`phyhelper speed`).
   * **При подключении кабеля Ethernet** между Master и Satellite:
     `topomon` мгновенно гасит беспроводной backhaul:
     ```sh
     wpa_cli -p /var/run/wpa_supplicant-wl01 disable_network 0
     ```
     Транзитный трафик переключается на провод со скоростью 1G/2.5G. **Это предотвращает возникновение L2-петель (Broadcast Storms)** в мосте `br-lan` без необходимости запуска STP.
   * **При отключении кабеля**:
     `topomon` немедленно вызывает `enable_network 0`, беспроводной линк восстанавливается за сотни миллисекунд.
2. **Многоузловая топология (Multi-Hop Daisy-Chain)**:
   * `topomon` вычисляет метрики пути до Master (`hop_count`, `uplink_rate`, `cap_ip`) и инжектирует их в вендорные теги (Vendor Specific IEs) радиомаяков через `cfg80211tool`:
     * `cfg80211tool wl5 mesh_hop <count>`
     * `cfg80211tool wl5 mesh_capip <ip>`
     * `cfg80211tool wl5 mesh_ulrate <speed>`
     * `cfg80211tool wl5 mesh_ethmode <0|1>`
   * Это позволяет строить цепочки из нескольких роутеров (`Master -> RE1 -> RE2`), где каждый узел автоматически выбирает оптимальный маршрут с наименьшим количеством хопов и максимальной скоростью.

### 3.3. Автоматическое проводное сопряжение (`cab_meshd`)
Сервис `/usr/sbin/cab_meshd` обеспечивает сопряжение «из коробки»:
* При соединении нового роутера патч-кордом с Master, демоны `cab_meshd` на обоих концах обнаруживают друг друга через широковещательные служебные кадры.
* Master генерирует `NETWORK_ID`, передает зашифрованные ключи backhaul и переводит новый роутер из режима чистого маршрутизатора в `whc_re` без участия пользователя.

### 3.4. Координированный бесшовный роуминг (802.11k/v/r и Steering)
В отличие от режима ретранслятора, где клиентские устройства переключаются автономно:
* Демоны `ssid-steering` и `bsd` собирают данные телеметрии (RSSI, SNR, канальная загрузка) со всех узлов сети через ubus/MQTT.
* Точки доступа передают клиентам таблицы соседних BSSID (802.11k Neighbor Reports).
* При ухудшении сигнала смартфона у головного роутера Master отправляет клиенту кадр **802.11v BSS Transition Management Request (BTM)**, директивно указывая BSSID сателлита с максимальным уровнем сигнала.

### 3.5. Синхронизация конфигурации через MQTT (`xq_info_sync_mqtt`)
* Головной роутер (CAP) является единственным источником конфигурации.
* При смене SSID, пароля Wi-Fi, гостевой сети или списков родительского контроля на Master, сервис `xq_info_sync_mqtt` по защищенному протоколу MQTT через ubus мгновенно применяет изменения на всех узлах Mesh.

### 3.6. Поддержка Wi-Fi 7 Multi-Link Operation (MLO Backhaul Bonding)
* Для маршрутизаторов поколения Wi-Fi 7 (BE3600 / RD15) транзитная сеть Backhaul не привязана жестко к одному диапазону 5 ГГц.
* Скрипт `/lib/mimesh/mimesh_init.sh` при флаге `bh_mlo_support='1'` создает виртуальные MLD-устройства:
  * На Master (CAP): `bhap_mld0` с подчиненными VAP `wl4` (2.4G) и `wl5` (5G).
  * На Satellite (RE): `bhsta_mld0` с подчиненными станциями `wl10` (2.4G) и `wl01` (5G).
* Режим агрегации настраивается параметром `CSwOpts='0x31'` и флагом `mesh_mlolink='1'`.
* MAC-адреса служебных BSSID вычисляются утилитой `calcbssid` на базе аппаратного MAC радиочипа (`calcbssid -i2 -m $dev_macaddr` для AP и `-i1` для STA), предотвращая конфликты с пользовательскими сетями.
* В результате при наличии помех на канале 5 ГГц (DFS или радарные импульсы) трафик между узлами мгновенно и без разрыва сессий дублируется через канал 2.4 ГГц.

## 4. Сравнительная матрица двух режимов моста

| Параметр | Сценарий А: Реле (`wifiapmode`) | Сценарий Б: Mesh (`whc_re`) |
| :--- | :--- | :--- |
| **Инициирование** | Веб-интерфейс: «Режим ретранслятора» | Кнопка Mesh / приложение Mi Home |
| **Интерфейс STA** | `wl02` (5 ГГц) / `wl12` (2.4 ГГц) | `wl01` (5 ГГц) / `wl10` (2.4 ГГц) |
| **Ключевой флаг UCI** | `option extap '1'` | `option backhaul '1'`, `option wds '1'` |
| **Канальный режим в ядре**| **3-address + Qualcomm DP ExtAP (L2 MAT)** | **True 4-address WDS (`wds_enabled=1`)** |
| **Трансляция адресов** | Выполняется подмена MAC и Proxy-ARP/NDP | **Отсутствует (честный прозрачный L2)** |
| **Видимость MAC на Master**| Виден **только MAC STA** (`56:4f:3b:ec:27:5f`) | Видны **все реальные MAC-адреса** хостов |
| **Целевая сеть** | Любой открытый/пользовательский SSID | Скрытая служебная сеть `MiMesh_*` |
| **Совместимость с AP** | **Любая точка доступа** (OpenWrt, ASUS...) | Только головной роутер Xiaomi Mesh |
| **Защита от петель (Loop)**| ❌ Нет (риск Broadcast Storm при кабеле) | ✅ Демон `topomon` отключает Wi-Fi при кабеле |
| **Бесшовный роуминг** | ❌ Автономный роуминг клиента (нет 802.11v BTM) | ✅ Координированный `ssid-steering` (802.11k/v) |
| **Синхронизация настроек**| ❌ Настраивается раздельно | ✅ Автоматическая через `xq_info_sync_mqtt` |
| **Аппаратный оффлоад PPE**| ✅ Через ECM + FSE (`src_interface_check=0`) | ✅ Через ECM + PPE Bridge Manager (AST) |

## 5. Результаты глубокого исследования и закрытие сомнительных мест

Сопоставление живых дампов телеметрии и последующий ассемблерный реверс-инжиниринг проприетарных модулей драйвера QSDK позволили **однозначно и математически строго разрешить ключевые вопросы**:

### 5.1. Разрешение вопроса №1: Доказательство механизма Qualcomm DP ExtAP (L2 MAT + Proxy-ARP/NDP)

* **Эмпирический факт из дампов**:
  * В дампе клиента (`192.168.11.22`) на 2.5G порту `eth1` моста `br-lan` активен проводной клиент с реальным MAC `00:25:22:aa:62:0b`.
  * В дампе Master (`192.168.11.23`) в таблице моста `brctl showmacs br-lan` на радиопорту 6 (`hostap_mld0`) зарегистрирован **только один MAC-адрес: `56:4f:3b:ec:27:5f`** (собственный MAC STA-адаптера `wl02` клиента). Реальный MAC `00:25:22:aa:62:0b` на стороне Master не появляется.
* **Ассемблерный анализ драйвера (`tmp/rootfs/lib/modules/5.4.213/umac.ko`)**:
  В закрытом модуле ядра `umac.ko` экспортируются функции Qualcomm DP ExtAP:
  * `dp_extap_attach` (offset `0x250284`)
  * `dp_extap_detach` (offset `0x2502a0`)
  * `dp_extap_rx_process` (offset `0x25068c`)
  * `dp_extap_tx_process` (offset `0x250e3c`)
  
  Деассемблирование `dp_extap_tx_process` (вспомогательная функция `_1639` по адресу `0x250964`) выявило точный алгоритм:
  1. **ARP-пакеты (`EtherType 0x0806`)**:
     * Драйвер извлекает `Sender IP` (`r9`, смещение +28) и `Sender Hardware Address` (`r8`, смещение +22).
     * Заносит связку `IP -> Real Client MAC` во внутреннюю хеш-таблицу MAT (функция `_3518` по адресу `0x24f934`).
     * Заменяет `Source MAC` в Ethernet-заголовке кадра (смещение +6) на собственный MAC-адрес адаптера STA (`wl02`).
     * Заменяет `Sender MAC` внутри тела ARP-запроса на MAC-адрес адаптера STA.
  2. **IPv4 Unicast (`EtherType 0x0800`)**:
     * Анализирует L4-протокол: для DHCP (UDP порты 67/68, Magic Cookie `0x63825363`) транслирует MAC в заголовке DHCP-запроса.
     * Для всего исходящего unicast-трафика безусловно перезаписывает `Source MAC` в Ethernet-заголовке на MAC адаптера STA (`0x250b08`: `mov r1, r5; add r0, r4, #6; mov r2, #6; bl qdf_mem_copy`).
  3. **IPv6 Unicast & NDP (`EtherType 0x86dd`)**:
     * Анализирует протокол: для ICMPv6 (`NextHeader 58 / 0x3a`) перехватывает Neighbor Solicitation (тип 135) и Neighbor Advertisement (тип 136).
     * Сохраняет IPv6-адрес клиента и его реальный MAC в таблицу MAT, после чего подменяет L2 MAC на STA MAC.
  4. **Обратный поток на приеме (`dp_extap_rx_process` по адресу `0x25068c`)**:
     * Кадры, приходящие от Master, имеют Destination MAC = STA MAC (`56:4f:3b:ec:27:5f`).
     * Функция `_1636` (по адресу `0x2502b8`) ищет Destination IP во внутренней хеш-таблице MAT.
     * Восстанавливает оригинальный MAC-адрес целевого клиента (`00:25:22:aa:62:0b`) в Ethernet Destination MAC.
     * Функция `_1381` (по адресу `0x25089c`) производит инкрементальный пересчет контрольных сумм IP/UDP/ICMP.
     * Пакет передается дальше в сетевой стек Linux и коммутируется в локальный мост `br-lan`.

* **Вывод**:
  Master AP физически не знает и не может знать MAC-адрес `00:25:22:aa:62:0b`, поскольку все кадры в радиоэфире передаются с MAC-адресом клиента `wl02`.
  **Именно благодаря L2 MAT режим `wifiapmode` работает с АБСОЛЮТНО ЛЮБОЙ сторонней точкой доступа (OpenWrt, ASUS, Keenetic, MikroTik, Cisco) без необходимости поддержки нестандартного WDS.**

2. **Реализация чистого моста WDS (OpenWrt-to-OpenWrt)**:
   * На передающей AP: `option wds '1'`.
   * На принимающей STA: `option wds '1'`.
   * Позволяет сохранить неизменными все оригинальные MAC-адреса хостов домашней сети в единой L2-таблице моста без применения MAT-трансляции.

### 8.1. Анатомия сбоя: что именно ломается при попытке запустить схему WDS/NAWDS в OpenWrt 24

В рамках ранних экспериментов для связки двух RD15 на OpenWrt 24 предлагалась следующая схема:
1. На стороне AP: `wlanconfig ath1 nawds mode 2 -cfg80211` и `wlanconfig ath1 nawds override 1 -cfg80211`.
2. На стороне STA: `iw dev ath11 set 4addr on` + добавление интерфейса в Linux-мост `brctl addif br-lan ath11`.
3. В конфигурации: `option wds '1'`.

При практической проверке этой схемы возникают скрытые аномалии: линк формально устанавливается, но пакеты теряются, SSH зависает через несколько секунд, трафик проводных клиентов за мостом не проходит, а скорость падает в разы. Анализ исходников QSDK 12.4 в `/home/romikb/repo.12.4/qsdk/` раскрывает физику каждого из этих явлений:

#### 1. Крах аппаратного оффлоада PPE Direct Switch (`dp_ppeds.c:1598`)
В файле `qca-wifi/component_dev/dp/wifi3.0/be/dp_ppeds.c` (блок инициализации аппаратного виртуального порта PPE Direct Switch):
```c
/*
 * Check if PPEDS could be enabled for Vdev
 */
if (vdev->wrap_vdev || vdev->nawds_enabled ||
    vdev->opmode == wlan_op_mode_monitor ||
    vdev->mesh_vdev || vdev->mesh_rx_filter) {
        dp_err("Unsupported Vdev config for id:%d", vdev_id);
        ret = QDF_STATUS_E_NOSUPPORT;
        goto fail1;
}
```
* **Прямое следствие**:
  Команда `wlanconfig ath1 nawds mode 2` устанавливает флаг `vdev->nawds_enabled = 1`.
  При этом модуль кремниевого акселератора PPE Direct Switch немедленно отклоняет VAP с ошибкой **`QDF_STATUS_E_NOSUPPORT`**!
  Аппаратный мост между кремнием Wi-Fi (QCN6432) и кремнием коммутатора PPE (2.5G Line Rate) **полностью отключается**. Вся передача данных сваливается в медленный программный путь процессора Linux (медленный путь `sk_buff`).

#### 2. «Кремниевая черная дыра»: сброс 4-адресных кадров в драйвере (`dp_wds_rx_policy_check`)
В файле `qca-wifi/cmn_dev/dp/wifi3.0/dp_txrx_wds.c` (функция L2-фильтрации на аппаратном кольце приема):
```c
int dp_wds_rx_policy_check(uint8_t *rx_tlv_hdr,
                           struct dp_vdev *vdev,
                           struct dp_txrx_peer *txrx_peer)
{
    ...
    fr_ds = hal_rx_mpdu_get_fr_ds(hal_soc, rx_tlv_hdr);
    to_ds = hal_rx_mpdu_get_to_ds(hal_soc, rx_tlv_hdr);
    rx_3addr = fr_ds ^ to_ds;
    rx_4addr = fr_ds & to_ds;

    if (vdev->opmode == wlan_op_mode_ap) {
        if ((!txrx_peer->wds_enabled && rx_3addr && to_ds) ||
            (txrx_peer->wds_enabled && !rx_mcast &&
            (rx_4addr == rx_policy_ucast)) ||
            (txrx_peer->wds_enabled && rx_mcast &&
            (rx_4addr == rx_policy_mcast))) {
            return 1; // Кадр валиден, принять в стек
        }
    }
    return 0; // СБРОС (SILENT DROP)
}
```
* **Прямое следствие**:
  Команда `wlanconfig nawds` НЕ выставляет флаг `txrx_peer->wds_enabled`! Этот флаг в QSDK активируется только специализированным ioctl `cfg80211tool wl0 wds 1` через `dp_txrx_peer_wds_tx_policy_update()`.
  В результате для подключенной станции параметр `txrx_peer->wds_enabled == 0`.
  Входное условие `(!txrx_peer->wds_enabled && rx_3addr && to_ds)` жестко разрешает прием **ИСКЛЮЧИТЕЛЬНО 3-адресных кадров**!
  Когда клиентская станция (на которой выполнено `iw dev ... set 4addr on`) шлет 4-адресный кадр (`rx_4addr == 1`), условие не выполняется, и функция возвращает **`0`**.
* **Симптом**: В интерфейсе роутера линк отображается как «подключен», сигнал отличный (-55 dBm), WPA2-рукопожатие пройдено, но **трафик не идет вообще (0 байт передано/принято)**. Драйвер отбрасывает кадры на аппаратном уровне кольца дескрипторов RX без единого сообщения в `dmesg`.

#### 3. Агрессивный 5-секундный таймер аппаратной таблицы AST (`DP_AST_AGING_TIMER_DEFAULT_MS`)
В файле `qca-wifi/cmn_dev/dp/wifi3.0/dp_txrx_wds.c`:
```c
#define DP_AST_AGING_TIMER_DEFAULT_MS   5000 // 5000 миллисекунд (5 секунд!)
```
* **Прямое следствие**:
  В чистом 4-адресном WDS все MAC-адреса устройств, находящихся за станцией-мостом, должны регистрироваться в аппаратной таблице чипа QCN6432 — **AST (Address Search Table)** с типом `CDP_TXRX_AST_TYPE_WDS`.
  В кремнии Qualcomm таймер устаревания записи AST по умолчанию равен **всего 5 секундам**.
  Если устройство (например, проводной компьютер за сателлитом или умная розетка) ничего не передает в течение 5 секунд, чип вычищает его MAC-адрес из кремниевой таблицы.
  Когда на головную точку доступа AP поступает входящий пакет для этого устройства (например, входящее TCP-подключение, ping или запрос от другого хоста), поиск по AST дает промах (AST Miss).
  В отличие от проводных Ethernet-свитчей, которые при неизвестном MAC-адресе выполняют Broadcast/Flooding на все порты, радиомодуль Wi-Fi 3.0 **не имеет права флудить одноадресный пакет в радиоэфир** и молча его уничтожает.
* **Симптом**: Внезапные «замирания» сети. Первый ICMP-пакет ping всегда теряется, SSH-сессии подвисают при паузе в наборе текста, видеозвонки прерываются, пока клиент сам не инициирует исходящий трафик и не обновит запись AST.

#### 4. Потеря широковещательных ARP и зависимость от `qca-mcs`
* В стандарте 802.11 широковещательные кадры (Broadcast ARP Request "Кто имеет IP 192.168.1.X?") передаются точкой доступа в 3-адресном формате от собственного MAC.
* Чтобы доставить такой кадр хостам за WDS-станцией, драйвер AP обязан преобразовать broadcast в 4-адресный unicast-кадр и отправить его персонально в сторону станции-моста (`wds_tx_mcast_4addr`).
* Для этой операции ядро QSDK требует обязательной работы модуля **мультикаст-снупинга `qca-mcs.ko`** со специальными хуками в драйвер Wi-Fi.
* В ванильном OpenWrt модуль `qca-mcs.ko` либо не собран, либо не сконфигурирован. В результате широковещательные ARP-запросы от шлюза (DHCP-сервера) не проникают за беспроводной мост. Хосты за мостом теряют шлюз из своей ARP-таблицы, а шлюз теряет хосты.

#### 5. Дроп пакетов модулем ECM (`net.ecm.src_interface_check=1`)
* В OpenWrt 24 модуль ускорения `qca-nss-ecm` по умолчанию включает проверку входного интерфейса (`net.ecm.src_interface_check = 1`).
* В режиме моста WDS, когда MAC-адреса хостов мигрируют между физическими портами свитча и беспроводным радиоинтерфейсом, ECM фиксирует несовпадение интерфейса-источника и сбрасывает сессии.
* В живом дампе со стоковой прошивки Xiaomi мы зафиксировали строго:
  ```text
  /proc/sys/net/ecm/src_interface_check = 0
  ```
  Без этого параметра модуль ECM разрушает мостовые потоки.

#### 6. Концептуальный разрыв: mac80211 vs Qualcomm Direct Connect
* В стандартном Linux mac80211 при включении `wds '1'` демон `hostapd` создает виртуальные сетевые интерфейсы для каждого подключенного пира (`wds-ath0-1` или `ath0.sta1`). Сетевой менеджер OpenWrt (`netifd`) слушает события ядра (rtnetlink) и автоматически добавляет каждый новый WDS-интерфейс в мост `br-lan`.
* В Qualcomm QSDK драйвер `wifi_3_0.ko` построен по архитектуре **Direct Connect (Full-MAC DP)**: он **не создает виртуальных интерфейсов для пиров**. Весь трафик идет через один мастер-интерфейс `ath0`/`ath1`, а распределение пакетов между пирами происходит внутри кремния через AST.
* `netifd` OpenWrt не понимает эту архитектуру: он не видит WDS-интерфейсов, не может назначить им правила моста и рассинхронизируется с состоянием Wi-Fi линка.

1. **Абсолютная межвендорная совместимость (100% Interoperability)**:
   * Стандарт IEEE 802.11 **никогда не стандартизировал протокол согласования 4-адресного WDS**. Из-за этого WDS Broadcom несовместим с WDS Qualcomm, WDS MediaTek не работает с Atheros, а mac80211 4addr работает только внутри OpenWrt.
   * Домашний роутер покупателя Xiaomi RD15 может быть любым: Keenetic, ASUS, TP-Link, GPON ONT от Huawei/ZTE/Sagemcom.
   * Благодаря `extap=1` ретранслятор для ЛЮБОЙ точки доступа выглядит как **самый обычный одиночный Wi-Fi клиент** (как смартфон или ноутбук). Это гарантирует 100% подключение «из коробки» к любой Wi-Fi сети без каких-либо настроек со стороны головного роутера.
2. **Динамическая таблица хостов на базе Radix Trie без жестких таймаутов**:
   * В `dp_extap_mitbl.c` трансляция адресов реализована на базе префиксного дерева (Radix Trie) в оперативной памяти маршрутизатора с динамическим выделением узлов (`mi_node_alloc`).
   * В ней **нет кремниевого 5-секундного таймера AST**! Записи не вычищаются при паузах в трафике, что полностью исключает подвисания SSH-сессий и потери пинга.
3. **Безупречная интеграция с кремниевым акселератором PPE и ECM**:
   * Для кремния PPE и модуля `ecm` весь радиоканал ассоциирован с одним MAC-адресом станции `wl02`.
   * Это позволяет кремниевому Flow Search Engine (FSE) напрямую оффлоадить сессии проводных клиентов через `ecm_wifi_plugin.ko` на полной скорости линии 2.5 Gbps Line Rate (при условии `src_interface_check=0`).
4. **Защита от широковещательных штормов и петель**:
   * В отличие от прозрачного L2 WDS, пропускающего любые Ethernet-фреймы (включая STP BPDU), станция с `extap=1` пропускает только авторизованный IP/ARP/NDP трафик, предотвращая петли коммутации при случайном подключении кабеля Ethernet.

### 8.3. Итоговое руководство к действию для OpenWrt 24 на RD15

Чтобы исключить возникновение «непонятных проблем» и обеспечить стабильную работу беспроводного моста в OpenWrt 24:

1. **Полностью отказаться от попыток настройки чистого WDS через `nawds`**:
   * Удалить вызовы `wlanconfig ... nawds mode 2` из скриптов инициализации, так как они ломают PPE Direct Switch (`dp_ppeds.c`).
2. **Внедрить полноценную поддержку `option extap '1'` в OpenWrt 24**:
   * В скрипте [`mac80211.sh`](file:///home/romikb/openwrt/target/linux/ipq53xx/rd15/base-files/lib/netifd/wireless/mac80211.sh) при обнаружении `extap '1'` для STA вызывать:
     ```sh
     cfg80211tool "$ifname" extap 1
     iw dev "$ifname" set 4addr on
     ```
   * Включать STA-интерфейс в мост `br-lan`.
3. **Обязательно применить системный тюнинг ECM**:
   * Добавить в `/etc/sysctl.d/11-ecm-bridge.conf`:
     ```text
     net.ecm.src_interface_check = 0
     ```
   Это устранит сброс ускоренных пакетов при передаче через мост.
4. **Для связки двух RD15 в режиме полноценного Mesh**:
   * Использовать либо подход с `extap='1'` (простой и надежный мост), либо разрабатывать полноценную интеграцию QCA Mesh на скрытых интерфейсах с вызовами `cfg80211tool <ifname> wds 1` и демоном `topomon`.
