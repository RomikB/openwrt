# Миграция драйвера свитча Motorcomm YT9215S на открытые исходники (Linux 5.4 QSDK -> Linux 6.6 DSA)

## 1. Цели проекта

### 1.1 Глобальная цель
* **Полноценная интеграция в upstream Linux 6.6+ в архитектуре DSA (Distributed Switch Architecture)**:
  * Разработка чистого открытого драйвера `drivers/net/dsa/motorcomm/yt9215s.c` без использования устаревшего `swconfig`.
  * Каждый физический порт свитча представляется отдельным сетевым интерфейсом (`lan1`, `lan2`, `lan3`, `wan`).
  * Аппаратный L2 offload через стек Linux Bridge (`bridge vlan`, `switchdev`).
  * Полный отказ от проприетарных блобов ядра.

### 1.2 Текущие промежуточные цели
1. **Верификация работы открытого драйвера на ядре Qualcomm QSDK 5.4.213** на маршрутизаторе **Xiaomi Router BE3600 (RD15)**.
2. **Верификация работы драйвера на оригинальном стоковом ядре Xiaomi**, где **невозможно изменить Device Tree (DTC/DTB)** из-за залоченного окружения/подписи загрузчика.

### 1.3 Ключевые требования к производительности
1. **Аппаратный L2 Forwarding (Line Rate 1 Gbps, 0% CPU)**:
   * Трафик между портами локальной сети (LAN ↔ LAN) коммутируется аппаратно матрицей свитча YT9215S. Процессор IPQ5332 не участвует в передаче L2-пакетов.
2. **Аппаратное L3 ускорение Qualcomm PPE / ECM (Line Rate 2.5 Gbps, ~0% CPU)** (для ядра 5.4):
   * Сохранение связки с драйверами `qca-nss-dp` и `qca-nss-ppe`.
   * Реализация и экспорт функции обратного вызова `portmap_get_by_vid`, необходимой диспетчеру Qualcomm ECM/PPE для аппаратной маршрутизации WAN ↔ LAN.
3. **Совместимость с Userland (OpenWrt и сток)**:
   * Для ветки ядра 5.4: поддержка интерфейса `swconfig` для штатного управления через LuCI/netifd и сохранение `/proc/smi`, `/proc/mib` для утилиты `/usr/sbin/switch_ctl`.
   * Для ветки ядра 6.6: нативный Linux DSA (`ip link`, `bridge vlan`).

## 2. Результаты реверс-инжиниринга стокового блоба (`yt_switch.ko`)

Дизассемблирование и аудит бинарного модуля `vendor_feed/kmod-yt-9215s-driver-vendor/files/lib/modules/5.4.213/yt_switch.ko` выявили точные механизмы его работы и дали ответ на ключевой вопрос: **почему в стоковом DTS нет узла свитча?**

### 2.1 Механизм инициализации стокового драйвера
В отличие от стандартных драйверов ядра, стоковый блоб **не использует `of_match_table` и `mdio_driver_register`**. Он полностью игнорирует стандартный механизм связывания Device Tree.

Последовательность шагов в функции `init_module()` (`_546`):
1. **Аппаратный сброс чипа по GPIO (`_924`)**:
   * Драйвер напрямую вызывает:
     ```c
     gpio_request(510, "yt-hw-reset");
     gpiod_direction_output_raw(desc, 0); // Reset LOW
     usleep_range(20000, 30000);
     gpiod_set_raw_value(desc, 1);        // Reset HIGH
     usleep_range(50000, 60000);
     printk("[yt_switch] reset success\n");
     gpio_free(510);
     ```
   * *Примечание*: GPIO 510 ядра соответствует аппаратному выводу GPIO 51 процессора IPQ5332 (базовый номер 459 + 51 = 510).
2. **Прямой поиск шины MDIO по системному пути (`_735`)**:
   * Драйвер ищет узел шины по жестко зашитому строковому пути:
     ```c
     struct device_node *np = of_find_node_opts_by_path("/soc/mdio@90000", NULL);
     struct mii_bus *bus = of_mdio_find_bus(np);
     printk("[yt_switch] mdio-bus init success\n");
     ```
   * Сохраняет указатель `mii_bus` в глобальную переменную. Все последующие операции чтения/записи идут через `mdiobus_read()` и `mdiobus_write()` по SMI-адресу свитча (0x1D).
3. **Инициализация L2-матрицы чипа**:
   * Настройка задержек RGMII/SGMII, изоляции портов и дефолтных PVID.
4. **Регистрация подсистемы `swconfig` (`miwifi_yt_swconfig_init`)**:
   * Создание виртуального свитча `switch1` с портами 0..5 (порт 0 — CPU RGMII uplink, порты 1..3 — LAN, порт 4 — WAN, порт 5 — SerDes 2.5G uplink).
5. **Ворккью / таймер отслеживания физических линков (`_1029`)**:
   * Периодический опрос внутренних PHY портов 1..4:
     `[yt_switch] Lan%d: Phy%d Link Up - %uMb/%s` или `Link Down`.
   * Передача события carrier в стек сетевых интерфейсов (`netif_carrier_on/off` для `eth0.1`, `eth0.2`, `eth0.3`).
6. **Регистрация интерфейсов Procfs**:
   * `/proc/smi` и `/proc/mib` (чтение/запись регистров и MIB-счетчиков).
   * `/proc/portmap` (привязка портов к VLAN).
7. **Экспорт коллбэка аппаратного ускорения**:
   * Установка глобального указателя `portmap_get_by_vid` для взаимодействия с Qualcomm ECM / PPE.

### 2.2 Почему открытый драйвер из SDK (`kmod-yt-9215s-driver`) молчал в `dmesg`
В открытом SDK `OpenEmbeddedBSP/motorcomm-yt9215-switch-sdk`:
* Использован классический `mdio_module_driver()`:
  ```c
  static const struct of_device_id yt9215rb_of_match[] = {
      { .compatible = "motorcomm,yt9215rb",},
      { /* sentinel */ },
  };
  ```
* Функция `probe()` вызывается ядром **только при обнаружении узла с compatible "motorcomm,yt9215rb"** на шине MDIO.
* Так как в стоковом DTS Xiaomi этого узла нет (стоковый блоб обходился без него), ядро просто загрузило модуль в оперативную память, но `probe()` не запустился ни разу.
* Кроме того, в сыром SDK Motorcomm **полностью отсутствуют** код `swconfig`, код опроса линков портов и связка с `netif_carrier`.

## 4. Стратегия работы со стоковым ядром (Без изменения DTC/DTS)

Поскольку на стоковом ядре невозможно пересобрать или подменить Device Tree Blob (DTB), открытый драйвер должен поддерживать **двойной режим инициализации (Dual-Mode Probe)**:

```c
static int __init yt9215_module_init(void)
{
    struct device_node *mdio_node;
    struct mii_bus *bus;

    // 1. Попытка стандартной регистрации через MDIO Device Tree
    // Если в DTS есть узел "motorcomm,yt9215rb", сработает стандартный probe
    if (mdio_driver_register(&yt9215_mdio_driver) == 0) {
        if (yt9215_device_probed)
            return 0; // Успешно привязались через DT
    }

    // 2. FALLBACK РЕЖИМ (для стокового ядра и стокового DTS):
    pr_info("[yt9215] DT node not found, activating legacy stock probe fallback...\n");

    // Аппаратный сброс свитча (GPIO 510)
    yt9215_hardware_reset(510);

    // Прямой поиск шины MDIO процессора
    mdio_node = of_find_node_by_path("/soc/mdio@90000");
    if (!mdio_node) {
        pr_err("[yt9215] Failed to find /soc/mdio@90000 in device tree!\n");
        return -ENODEV;
    }

    bus = of_mdio_find_bus(mdio_node);
    of_node_put(mdio_node);
    if (!bus) {
        pr_err("[yt9215] MDIO bus not ready yet!\n");
        return -EPROBE_DEFER;
    }

    // Инициализация драйвера с найденной шиной
    return yt9215_attach_manual(bus, 0x1D);
}
```

Этот подход гарантирует:
1. Модуль загружается и работает **на оригинальной прошивке Xiaomi** поверх заводского ядра без единого изменения в дереве устройств.
2. Модуль работает **на нашем QSDK 5.4 ядре** со стоковым DTS.
3. При появлении узла в DTS (например, при переходе на ядро 6.6) модуль автоматически использует стандартный механизм ядра.

### 7.1. Патч `001-boardprofile.patch` (Привязка шины доступа SMI)
* **Файл**: `switch_sdk/common/boardprofile/bprofile_YT9215SC_default_demo.c`
* **Какую проблему решает**: В исходном SDK метод доступа к регистрам чипа в структуре платы `yt9215sc_default_swDescp` не был настроен на реальную шину (значение было по умолчанию/отключено). Уровень абстракции FAL (Forwarding Abstraction Layer) не имел функций чтения/записи физических регистров через шину MDIO.
* **Что сделано**:
  1. Объявлены внешние функции низкоуровневого доступа, реализованные в драйвере:
     ```c
     extern uint32_t rd15_smi_read(uint8_t phy_addr, uint8_t reg_addr, uint16_t *pVal);
     extern uint32_t rd15_smi_write(uint8_t phy_addr, uint8_t reg_addr, uint16_t val);
     ```
  2. В дескрипторе коммутатора задан метод `SWCHIP_ACC_SMI`, аппаратный адрес свитча `phyAddr = 0x1D` и привязаны указатели `smi_read`/`smi_write` к объявленным функциям.
  3. Активировано описание портов `YT9215sc2SGFibPortDescp`: 5 медных GE-портов (MAC 0..4) и высокоскоростной 2.5G SerDes Uplink (MAC 8, тип `ETH_TYPE_GE25`, среда `PORT_MEDI_FIBER`).

### 7.2. Патч `002-enable-yt9215sc-profile.patch` (Выбор профиля платы)
* **Файл**: `switch_sdk/config/kernel_module/env.h`
* **Какую проблему решает**: При вызове функции инициализации `yt_init()` модуль завершался с ошибкой `CMM_ERR_NOT_INIT` (код 4). В функции `cal_board_profile_init()` SDK выполняет линейный перебор всех профилей и выбирает **первый встретившийся с флагом YES**. В исходном коде первым был включен `Board_YT9215_Default_Demo=YES` (пустой профиль без SMI-доступа), из-за чего чип не мог инициализироваться.
* **Что сделано**:
  1. Отключен дефолтный профиль: `# Board_YT9215_Default_Demo is not set`.
  2. Принудительно включен целевой профиль: `export Board_YT9215SC_Default_Demo=YES`.
  3. В результате SDK безошибочно выбирает профиль `bprofile_YT9215SC_default_demo.c` с настроенным доступом к чипу по SMI 0x1D.

  * Результирующий файл модуля ядра собирается как `yt_switch.ko`, обеспечивая 100% совместимость со стоковым окружением и правилами автозагрузки `/etc/modules.d/57-yt_switch`.

### 7.4. Патч `004-driver.patch` (Основной автономный драйвер свитча)
* **Файл**: `yt9215rb_mdio_driver/yt9215rb.c`
* **Какую проблему решает**: Исходный файл `yt9215rb.c` из SDK представлял собой заготовку, которая не могла работать на реальном роутере:
  - Ждала несуществующий узел в Device Tree (`motorcomm,yt9215rb`) и не запускалась.
  - Не производила сброс по GPIO, оставляя свитч в зависшем состоянии.
  - Не имела интеграции с подсистемой `swconfig`.
  - Не отслеживала состояние линков кабелей (Linux-интерфейсы оставались в состоянии `NO-CARRIER`).
  - Не инициализировала SerDes 2.5G и контроллер светодиодов.
  - Содержала неверную конфигурацию TPID и тегирования VLAN (пакеты от ядра Linux отбрасывались аппаратно).
  - Не имела хуков аппаратного ускорения маршрутизации Qualcomm PPE/ECM.

Патч полностью переписывает файл драйвера, реализуя 8 ключевых архитектурных подсистем:

#### 1. Автономная инициализация (DT-less Probe Fallback)
* **Аппаратный сброс**: Захват GPIO 510 ядра (соответствует аппаратному выводу GPIO 51 процессора IPQ5332), удержание уровня LOW в течение 100 мс, затем перевод в HIGH на 150 мс для полного аппаратного сброса логики чипа.
* **Поиск шины MDIO**: Драйвер находит узел шины процессора `/soc/mdio@90000` через `of_find_node_opts_by_path()` и получает дескриптор `mii_bus` через `of_mdio_find_bus()`. Драйвер стартует автоматически без необходимости менять Device Tree роутера.

#### 2. Низкоуровневые операции шины SMI
* `rd15_smi_read` и `rd15_smi_write`: Реализация стандартных 16-битных операций чтения/записи MDIO через шину процессора, используемых SDK для конфигурации таблиц L2.
* `yt_direct_smi_read` и `yt_direct_smi_write`: Реализация прямого 32-битного доступа к внутренним регистрам свитча через косвенную адресацию PHY 0x1D (необходимо для управления SerDes, LED и отладки через `/proc/smi`).

#### 3. Аппаратная инициализация L2 и 2.5G SerDes (`yt_hw_setup`)
* Настройка скрытых регистров SMI (`0x000f0004`, `0x000f0008`, `0x000f0000`).
* Инициализация аналоговых блоков SerDes PHY 0 и 1 (`0x00303000 = 0x1a5`, `0x00303020 = 0x1a5`).
* Инициализация Port 5 (Uplink к процессору IPQ5332 SerDes 2.5G):
  - Принудительная установка параметров: 2500 Mbps, Full Duplex, Rx/Tx Flow Control включены (`yt_port_mac_force_set`).
  - Активация порта через регистры `0x0008008c = 0x27a` и `0x00080028 = 1`.
* Инициализация контроллера светодиодов LED (`0xd0000 = 0x20e002`, `0xd0004..0xd001c = 0x670`).

#### 4. Исправление тегирования VLAN и TPID (Root Cause сброса пакетов WAN/DHCP)
* **Ingress TPID Profiles**: Через функцию `yt_vlan_igrTpid_set(0, tpid)` в регистры парсера `0x210000` прописаны сигнатуры EtherType `0x8100` (CTAG) и `0x88a8` (STAG). Без этого свитч не распознавал 802.1Q-теги от ядра Linux и отбрасывал пакеты DHCP Discover на входе Port 5.
* **Egress Tag Mode для Port 5 (CPU Uplink)**: Принудительно установлен в `VLAN_TAG_MODE_TAGGED` (`yt_vlan_port_egrTagMode_set`). Без этого свитч срезал теги входящих пакетов из WAN, и подинтерфейс `eth0.1` не получал сетевой трафик.
* **Внешние порты (1..3)**: Установлены в режим `VLAN_TAG_MODE_UNTAGGED`, а в регистрах парсера внешних портов (`0x00210010..0x0021001c`) очищены маски в соответствии со стоковой заводской прошивкой.
* **Дефолтная топология VLAN**:
  - VLAN 1 (WAN): Port 3 (untagged) + Port 5 (tagged). PVID = 1.
  - VLAN 2 (LAN2): Port 2 (untagged) + Port 5 (tagged). PVID = 2.
  - VLAN 3 (LAN1): Port 1 (untagged) + Port 5 (tagged). PVID = 3.

#### 5. Интеграция с подсистемой `swconfig`
* Зарегистрирован виртуальный коммутатор `switch1` (7 портов, 4096 VLAN).
* Реализованы все стандартные коллбэки:
  - `get_port_pvid` / `set_port_pvid` (чтение и запись PVID порта).
  - `get_port_link` (опрос состояния линка, дуплекса и скорости).
  - `get_port_stats` (аппаратные 64-битные счетчики байт и пакетов).
  - `get_vlan_ports` / `set_vlan_ports` (динамическая настройка членства портов в VLAN с автоматической установкой `VLAN_TAG_MODE_TAGGED` для транковых портов и `UNTAGGED` для портов доступа).
  - Глобальные атрибуты: `enable_vlan`, `mib`, `info`.

#### 6. Фоновый опрос линков (Polling Worker) и Carrier Tracking
* Запущен выделенный однопоточный ворккью `yt_switch_wq`, каждую секунду вызывающий `yt_link_poll_worker()`.
* Воркер опрашивает состояние внутренних PHY-портов через `yt_port_link_status_all_get()`.
* При изменении состояния кабеля драйвер логирует событие:
  `[yt_switch] Lan%d: Phy%d Link Up - %uMb/%s` или `Link Down`.
* Мгновенно передает событие в сетевой стек Linux (`netif_carrier_on()` / `netif_carrier_off()`) для виртуальных интерфейсов `eth0.1..eth0.3` согласно таблице соответствия `/proc/portmap`.

#### 7. Управляющие интерфейсы Procfs
* `/proc/smi`: Позволяет читать и писать любые 32-битные регистры свитча напрямую (`echo read 0xd0004 > /proc/smi`), что дает возможность динамической калибровки и работы утилиты `/usr/sbin/switch_ctl`.
* `/proc/mib`: Включение и чтение подробной аппаратной статистики ошибок (RX_DROP, FCSERR, QM_FILTER).
* `/proc/portmap`: Чтение и динамическая смена привязки физических портов свитча к сетевым интерфейсам Linux (`1` $\rightarrow$ `eth0.3`, `2` $\rightarrow$ `eth0.2`, `3` $\rightarrow$ `eth0.1`).

#### 8. Аппаратный оффлоад Qualcomm PPE / ECM (`portmap_get_by_vid`)
* Реализована функция `yt_portmap_get_by_vid`, привязанная к слабому символу ядра `portmap_get_by_vid`.
* Позволяет аппаратным ускорителям процессора Qualcomm IPQ5332 (NSS / PPE / ECM) мгновенно определять целевой физический порт свитча по идентификатору VLAN (VID).
* Обеспечивает аппаратную маршрутизацию и NAT на скорости 2.5 Gbps без загрузки центрального процессора (CPU ~0%).

### 9.1 Две аппаратные ревизии роутера Xiaomi BE3600 (RD15)

Исследование реального устройства, заводских дампов и стоковой прошивки показало, что компания Xiaomi при производстве роутера BE3600 применяет стратегию параллельных поставок компонентов (second-source component sourcing). В зависимости от партии роутера на плате может быть распаян один из двух совершенно разных 2.5G PHY-трансиверов:

#### 1. Аппаратная ревизия с Qualcomm QCA8081 (PHY ID `0x004dd101`)
* **Физический чип**: Оригинальный 2.5-гигабитный Ethernet PHY-трансивер Qualcomm Atheros QCA8081.
* **Драйвер ядра**: Управляется **штатным открытым драйвером ядра Linux** `drivers/net/phy/at803x.c` (`CONFIG_AT803X_PHY=y`, распознается подсистемой PHYlib как `QCA808X ethernet`). Данный драйвер вкомпилирован напрямую в монолитное ядро (`vmlinux`), не требует внешних модулей и полностью поддерживается апстримом Linux.
* **Связка с сетевым стеком**: Трансивер напрямую связан с MAC `dp2` (`eth1`) и аппаратным ускорителем Qualcomm PPE (`switch0`), обеспечивая аппаратную маршрутизацию и NAT на полной скорости 2.5 Gbps без нагрузки на CPU.
* **Управление из Userspace**: Скрипты платформы Xiaomi (`lib_arch_phy_eth.sh`) проверяют наличие узла `/sys/bus/mdio_bus/devices/90000.mdio:0c/phy_id`. При обнаружении ID `0x004dd101` управление питанием и скоростью порта осуществляется через утилиту `switch_ctl` и свитч `switch0`.

#### 2. Аппаратная ревизия с Motorcomm YT8821 (PHY ID `0x4f51ea19`)
* **Физический чип**: Альтернативный китайский 2.5-гигабитный трансивер Motorcomm YT8821.
* **Драйвер ядра**: В оригинальной стоковой прошивке Xiaomi использовался закрытый бинарный модуль `vendor_feed/kmod-yt-phy-driver-vendor/files/lib/modules/5.4.213/yt_phy_module.ko`.
* **Управление из Userspace**: Скрипты платформы Xiaomi (`lib_arch_yt8821_phy_eth.sh`, `phyhelper`) взаимодействуют с чипом через кастомные файлы виртуальной файловой системы Sysfs: `/sys/module/yt_phy_module/port_status/port0/`.

### 9.2 Разработка открытого пакета `package/kernel/yt-phy-driver`

Для полного отказа от проприетарного блоба `kmod-yt-phy-driver-vendor` был разработан и интегрирован открытый пакет драйвера ядра:
* **Архитектурная основа**: Исходный код `package/kernel/yt-phy-driver/src/yt_phy_main.c` написан на базе официального открытого драйвера Frank Sae из ядра **Linux 6.12 mainline** (`drivers/net/phy/motorcomm.c`).
* **Бэкпортирование под ядро Linux 5.4 QSDK**:
  - Адаптация под API PHYlib ядра 5.4: вызов `genphy_c45_pma_read_abilities()`.
  - Динамическое переключение интерфейсов MAC ↔ PHY между 2500Base-X и SGMII в функции `yt8821_update_interface()`.
  - Прямой бесконфликтный доступ к paged-регистрам автосогласования через незаблокированные примитивы `__phy_read()` / `__phy_write()`.
* **Эмуляция интерфейса Sysfs стоковой прошивки**:
  - Реализован легковесный sysfs-слой совместимости по пути `/sys/module/yt_phy_module/port_status/port0/`.
  - Предоставлены атрибуты: `power` (up/down), `speed` (10/100/1000/2500/auto), `10_autoNeg`, `100_autoNeg`, `1000_autoNeg`, `2500_autoNeg`.
  - Системные скрипты OpenWrt / Xiaomi (`lib_arch_yt8821_phy_eth.sh`, `phyhelper`) продолжают работать в штатном режиме без единого изменения в пользовательском пространстве.
* **Отказ от проприетарных таймеров (0% лишней нагрузки на CPU)**:
  - Анализ стокового блоба показал наличие 1-секундного таймера `add_timer` / `miwifi_phy_timer_init`, который в цикле опрашивал регистр 0x11 и вызывал `dev_get_by_name("eth1")` + `netif_carrier_on/off`.
  - В открытом драйвере этот костыль исключен: отслеживание состояния линка и скорости возложено на стандартный событийный механизм ядра `phylib`, исключая нерациональные прерывания таймера ядра.
* **Независимость от других модулей**:
  - Модуль экспортирует 0 глобальных символов. Модули PPE, NSS, ECM и Wi-Fi от него не зависят.
* **Интеграция в билдсистему**:
  - Создан пакет `package/kernel/yt-phy-driver/Makefile` (`KernelPackage/yt-phy-driver`), собирающий `kmod-yt-phy-driver`.
  - Приоритет автозагрузки: `/etc/modules.d/57-yt-phy-driver`.
  - Пакет прописан в `DEVICE_PACKAGES` целевого профиля `xiaomi-rd15-qsdk` в `target/linux/ipq53xx/image/rd15.mk`, полностью заменив блоб `kmod-yt-phy-driver-vendor`.

### 9.3 Статус верификации и ограничение физического тестирования

2. **Поведение открытого модуля `yt_phy_module.ko`**:
   - Модуль успешно скомпилирован кросс-компилятором, включен в корневую файловую систему и загружается ядром при старте системы:
     ```
     [ 4.660919] yt_phy_module: Motorcomm YT8821 PHY driver initialized
     ```
   - Драйвер успешно регистрируется в подсистеме PHYlib ядра Linux (`phy_driver_register`).
   - Sysfs-интерфейс `/sys/module/yt_phy_module/port_status/port0/` полностью инициализируется:
     - Чтение `power` корректно возвращает текущее состояние (`up`).
     - Чтение `speed` возвращает статус согласования (`auto`).
     - Запись команд в sysfs отрабатывает без ошибок ядра.
   - Утилита `phyhelper link port 4` корректно опрашивает порт и возвращает статус:
     ```
     port:4 link:down lan
     ```
   - Поскольку физический чип YT8821 на плате отсутствует, драйвер находится в неактивном режиме ожидания (dormant) и не мешает работе параллельного чипа Qualcomm QCA8081.

#### Заключение по драйверу 2.5G PHY:
* Если собранная прошивка будет запущена на ревизии роутера Xiaomi BE3600 с чипом Motorcomm YT8821, ядро Linux автоматически обнаружит PHY ID `0x4f51ea19` на шине MDIO и передаст управление модулю `yt_phy_module.ko`.
* В кодовой базе проекта больше **не осталось закрытых бинарных модулей** для PHY/Switch:
  - Коммутатор 1G портов LAN1-3 / WAN: открытый `kmod-yt-9215s-driver` (протестирован, wire-speed).
  - Порт 2.5G LAN4 (Ревизия Qualcomm): открытый in-tree `at803x.c` (протестирован, wire-speed).
  - Порт 2.5G LAN4 (Ревизия Motorcomm): открытый `kmod-yt-phy-driver` (собирается, загружается, sysfs проверен; сквозной линк ожидает верификации на устройстве с YT8821).

## 10. Замена проприетарной утилиты `yt-9215s-client-vendor` на открытый `yt-9215s-client`

### 10.1 Проблема проприетарного блоба `switch_ctl`
В оригинальной прошивке Xiaomi и вендорном фиде утилита `/usr/sbin/switch_ctl` поставлялась в составе закрытого пакета `yt-9215s-client-vendor`:
* Бинарник был скомпилирован под проприетарный загрузчик динамических библиотек `/lib/ld-vendor.so.1` и библиотеку `libc-vendor`.
* Утилита критически необходима системным скриптам OpenWrt на Xiaomi RD15:
  - `lib_arch_port_map.sh`: вызовы `switch_ctl forward 0` (изоляция портов на время перенастройки VLAN) и `switch_ctl forward 1` (восстановление нормального форвардинга).
  - `lib_arch_phy_eth.sh`: вызовы `switch_ctl phy <id> autoNeg get`, `switch_ctl phy <id> autoNeg set <speed>`, `switch_ctl phy <id> power 0/1`.

### 10.2 Создание открытого пакета `package/network/utils/yt-9215s-client`
На основе реверс-инжиниринга интерфейса взаимодействия утилиты со свитчем была разработана открытая утилита `switch_ctl.c` в пакете `yt-9215s-client`:
* **Стандарт языка**: Чистый C99, без привязки к проприетарным libc.
* **Компиляция**: Штатный GCC OpenWrt с линковкой против стандартной `musl libc`. Зависимость от `libc-vendor` полностью ликвидирована.
* **Поддерживаемые команды**:
  - `switch_ctl forward 0/1` (управление изоляцией/форвардингом)
  - `switch_ctl sw_reg r/w <addr> [val]` (чтение/запись 32-битных регистров свитча)
  - `switch_ctl phy <id> autoNeg get/set [speed]` (чтение и установка автосогласования)
  - `switch_ctl phy <id> power 0/1` (управление питанием порта)
  - `switch_ctl phy <id> speed <spd> duplex <half/full>` (принудительный режим)
  - `switch_ctl phy <id> r/w <reg> [val]` (чтение/запись регистров PHY)
  - `switch_ctl phy <id> fc 0/1`, `switch_ctl phy game set/disable`, `switch_ctl fdb dump`.
* **Формат вывода**: Точно соответствует парсерам в shell-скриптах Xiaomi (`cut -d ":" -f 3 | xargs`).

### 10.3 Реализация ioctl-обработчика в `kmod-yt-9215s-driver` (`004-driver.patch`)
Оригинальный открытый SDK Motorcomm не содержал обработчика `ioctl` на файле `/proc/smi`. Для поддержки `switch_ctl`:
* В структуру `proc_ops yt_smi_proc_ops` добавлены поля `.proc_ioctl` и `.proc_compat_ioctl` (для ядер 5.6+) и `.unlocked_ioctl` / `.compat_ioctl` для ядра 5.4.
* Реализован диспетчер команд `yt9215rb_smi_ioctl`:
  - `0x200`: `fdb dump`
  - `0x201` / `0x202`: прямое чтение/запись регистров через `yt_direct_smi_read`/`yt_direct_smi_write`.
  - `0x204`: управление питанием порта через `yt_port_enable_set`.
  - `0x205` / `0x206`: получение и настройка маски скоростей автосогласования через `yt_port_phyAutoNeg_ability_get`/`set`.
  - `0x207`: принудительная установка скорости и дуплекса через `yt_port_phy_force_set`.
  - `0x208` / `0x209`: доступ к регистрам PHY через `rd15_smi_read`/`write`.
  - `0x20c`: переключение форвардинга через `yt_port_isolation_set`.

### 10.4 Особенность регистра `L2_PORT_ISOLATION_CTRLNm` и устранение аппаратной изоляции
В процессе интеграции был детально исследован аппаратный механизм изоляции портов свитча YT9215S:
* Аппаратный регистр `L2_PORT_ISOLATION_CTRLNm` (базовый адрес `0x180294`, шаг 4 байта на порт) хранит битовую маску **заблокированных (изолированных)** портов.
* **Штатный режим пересылки (`forward 1`):** маски изоляции для всех портов должны быть равны **`0x0`** (ни один порт не изолирован, все порты свободно обмениваются пакетами с портом процессора 5).
* **Блокировка пересылки (`forward 0`):** выставляются маски `0x3e, 0x3d, 0x3b, 0x37, 0x2f, 0x1f`, запрещающие портам передавать кадры друг другу.
* После корректной реализации логики `forward 1`/`forward 0` подтверждено:
  - При `switch_ctl forward 1` регистры `0x180294`..`0x1802a8` принимают значение `0x0`.
  - При старте роутера WAN-порт (`eth0.1` / Phy3) мгновенно получает IP-адрес по DHCP (`192.168.11.46`).
  - Все подкоманды `switch_ctl` отрабатывают штатно.

### 10.5 Интеграция в профили сборки
* **`target/linux/ipq53xx/rd15/target.mk`**: Пакет `yt-9215s-client-vendor` исключен из глобального списка `DEFAULT_PACKAGES`.
* **`target/linux/ipq53xx/image/rd15.mk`**:
  - В профиле `xiaomi-rd15-prebuild`: оставлен вендорный пакет `yt-9215s-client-vendor` (вместе с вендорными драйверами).
  - В профиле `xiaomi-rd15-qsdk`: подключен новый открытый пакет `yt-9215s-client` (вместе с открытыми `kmod-yt-9215s-driver` и `kmod-yt-phy-driver`).
